vindover@yandex.ru

## Как запустить

```
cp .env.example .env        # CANDIDATE=vindover@yandex.ru
docker compose up worker
docker compose run --rm exporter
node selfcheck.js out/result.jsonl   # необязательно, самопроверка результата
```

## Как устроено хранение и почему

Одна таблица `messages` (PK = `external_id`) плюс колонки `thread_key` и `parent_id`,
которые заполняются отдельным batch-проходом после того, как лента вычитана до конца.
PK на `external_id` даёт бесплатный `ON CONFLICT DO NOTHING` — повторно пришедшее
письмо не создаёт дубль. Разговоры — компоненты связности (union-find) по
`in_reply_to`/`references`, посчитанные одним проходом по всей таблице, а не
инкрементально при вставке: письмо, которое задним числом склеивает два разговора
(пример с E в задании), из-за этого не требует пересмотра уже вставленных строк.
Отдельная таблица `fetch_progress` хранит курсор — по нему воркер продолжает
докачку после рестарта.

## Если появится второй почтовый сервис

Код выгрузки (постраничный обход, ретраи, курсор) для него не нужен — вместо него
понадобится обработчик входящего потока (push). Так как своих `message_id` у
источника нет, придётся завести суррогатный `external_id` (например, `source:id`).
Union-find по ссылкам тоже не нужен — разговоры уже даны, `thread_key` для таких
писем просто берётся из готового разговора источника. Таблица `messages` и формат
экспорта переиспользуются без изменений; выгрузка и threading первого провайдера
не трогаются.

## Что произойдёт при одновременном запуске двух `worker` над одной базой

Реально работает только один: второй блокируется на Postgres advisory lock,
который берётся на всё время работы `worker` и снимается автоматически при
закрытии соединения, даже если процесс упал аварийно. Без этой блокировки было бы
два риска: гонка при обновлении `fetch_progress.next_cursor` (данные не
пострадали бы — вставка идемпотентна, но прогресс курсора мог бы потеряться) и то,
что оба воркера одновременно жгли бы rate limit провайдера.

## Есть ли шаг, который нельзя выполнить дважды подряд без последствий

Такого шага нет. Вставка писем — upsert по `external_id`, курсор в
`fetch_progress` можно перечитать и продвинуть повторно, а `thread_key`/`parent_id`
— чистый детерминированный пересчёт от текущего состояния таблицы `messages`, не
зависящий от истории вызовов. Поэтому и `worker`, и его повторный запуск после
рестарта, и повторный вызов `exporter` можно выполнять сколько угодно раз.

## Что решили не усложнять

Разговоры считаются одним batch-проходом union-find в памяти после полной
выгрузки, а не инкрементально при вставке каждого письма — так пример с письмом,
задним числом склеивающим два разговора, не требует пересмотра уже сохранённых
строк. Если бы сервису нужно было отдавать актуальные разговоры не только по
завершении, а прямо во время докачки, потребовался бы персистентный DSU с
частичным пересчётом на каждой вставке.

Также не стали заводить ORM или repository-слой — таблиц всего две, и прямой
Kysely/SQL проще и нагляднее абстракции ради абстракции.

## Что перестанет работать при десятикратном объёме писем

Первым упрётся batch-проход threading: он держит все `external_id`/`in_reply_to`/
`references` в памяти одного процесса и одним `UPDATE ... unnest(...)` переписывает
всю таблицу — при на порядок большем объёме это давление и на память, и на размер
одной транзакции. Второе узкое место — строго последовательный обход курсора:
постраничная выгрузка принципиально не параллелится (курсор общий), а rate limit
провайдера при этом никуда не девается, так что время полной выгрузки будет расти
линейно.
